# Harmonizer Studio — 全面架构评估与演进路线图

## 1. 核心价值锚定（Core Essence）

**项目本质**：Harmonizer Studio 是一个面向音乐创作者的 **乐理辅助 MIDI 编辑器**。其核心价值在于：在一个 Cubase 风格的钢琴卷帘窗中，让创作者无需手动推导乐理，即可通过可视化的调式推荐、和弦分析、以及一键式重配和声算子，快速探索音符组合的理论可能性。

**用户黄金路径（Golden Path）**：
1. **导入 MIDI** → 在钢琴卷帘窗中看到音符
2. **调式分析** → 系统自动识别当前调性 → 背景着色引导音阶内/外音
3. **选中音符 → 执行和声算子**（副属和弦、三全音替代等）→ 一键重映射音符 → 即时试听

> [!CAUTION]
> **绝对不可破坏的边界**
> - **钢琴卷帘窗的操作流畅度**：任何重构都不能降低音符绘制、拖拽、选择的响应性
> - **和弦分类器与调式分析器的正确性**：`ChordClassifier` 和 `ModeAnalyzer` 是核心乐理引擎，其算法精度是产品立命之本
> - **Cubase 式操作手感**：修饰键行为（Alt+拖拽复制、中键平移、Ctrl多选）与工具切换逻辑已经打磨成形，不可倒退
> - **Undo 系统的完整性**：所有编辑操作的可撤销链条

- **ARC-1**：将 TrackArranger 拆分为 `TrackLaneBase` + 5 个子类（`InstrumentLane`, `ChordLane`, `ModeLane`, `MarkerLane`, `TimeSigLane`），每个子类自行处理渲染与鼠标事件
- **ARC-2**：将所有可变引用改为 `const` 引用 + 显式 mutation 方法（如 `addClip()`, `removeClip()`, `updateClip()`），数据修改必须经过 Model 的中心化接口
- **ARC-3**：创建 `src/theory/HarmonyService.h` 作为乐理操作的 Facade，统一封装和弦分析、调式推荐、和声重配等高层操作
- **ARC-4**：引入 `TrackData` 变体类型或使用 `std::variant` / 类继承体系来区分轨道数据
- **ARC-5**：引入 `GenericSnapshotUndoAction<T>` 模板

### 2.3 效率与性能（Performance & Efficiency）

| 问题编号 | 问题描述 | 严重度 | 现状分析 |
|----------|----------|--------|----------|
| **PERF-1** | **钢琴卷帘窗背景每帧全量重绘** | 🔴 严重 | PianoRollCanvas 的 `paint()` 中每帧遍历 `getBarTimeline()` 和 Mode Track 事件来切割背景、计算每个像素行是否在音阶内。在长工程（100+ 小节）或高缩放下 CPU 占用会飙升。 |
| **PERF-2** | **斜线阴影绘制使用 clipRegion** | 🟡 中等 | 未分配区域的斜线阴影通过 `ScopedSaveState + reduceClipRegion` 实现，当区域碎片多时性能很差。 |
| **PERF-3** | **ModeAnalyzer 全量枚举** | 🟢 轻微 | [ModeAnalyzer.cpp L152-L199](file:///x:/AI project/和声重配GPT/src/core/ModeAnalyzer.cpp#L152-L199) 对 12 调 × 12 音阶 = 144 个候选进行逐一 Pearson 相关。对于实时场景虽然不是瓶颈（<1ms），但如果未来扩展音阶库到 50+ 种，复杂度会线性增长。 |
| **PERF-4** | **Listener 通知无节流** | 🟡 中等 | `triggerNoteListChanged()` 每次都立即同步通知所有 UI 组件重绘。在批量操作（如粘贴 100 个音符）时会造成 N 次无意义的 repaint。 |

**优化方案**：
- **PERF-1**：引入离屏缓存 (`juce::Image`) 用于静态背景网格。仅在缩放、滚动偏移、调式变化时重建缓存
- **PERF-2**：将斜线阴影预渲染为平铺纹理图案
- **PERF-3**：增加剪枝策略（如先用 in-scale 覆盖率 < 50% 快速排除），或异步执行
- **PERF-4**：引入批量操作模式 `BatchGuard`，在析构时统一触发一次通知

- **ROB-1**：为 `ChordClassifier` 和 `ModeAnalyzer` 建立 Google Test 单元测试套件，覆盖所有 30 种和弦品质
- **ROB-2**：改用 UUID 或时间戳复合 ID
- **ROB-3**：将选择状态抽取为独立的 `SelectionSet<int64_t>` 类，从 NoteEvent 中移除 `isSelected`
- **ROB-4**：为所有 Event 结构体添加 `static_assert(std::is_trivially_copyable_v<...>)` 编译期检查
- **ROB-5**：引入 `Result<T>` 类型或 `juce::Result` 用于所有可能失败的操作

## 推荐立即实施的 3 个杠杆点

> [!IMPORTANT]
> 以下三项基于全量代码审计后的综合判断，是 **投入产出比最高** 的切入点。
> 注意：由于深度审计发现了多个**致命级崩溃 Bug**（P0-1/8/9），原先的优先级需要调整。

### 🏆 杠杆点 1：修复三大致命崩溃隐患 (P0-1 + P0-8 + P0-9)

**理由**：这三个问题会导致 **程序崩溃** 和 **数据全量丢失**，是当前代码中的定时炸弹。不修复这些问题，任何功能开发都建立在流沙之上。

**工作内容**：
- **P0-1 工程保存**：重构 `ProjectFile` 使其接收 `TrackModel&`，完整序列化/反序列化所有轨道、事件、Clip 数据
- **P0-8 音频线程数据竞争**：引入双缓冲快照机制——UI 修改 `notes` 后生成只读快照，音频线程仅读快照
- **P0-9 VST 插件卸载竞争**：在切换/卸载插件前调用 `deviceManager.removeAudioCallback`，完成后重新添加；`allNotesOff()` 改为向 `pendingMidi` 发送 CC123 而非直接调 `processBlock`

### 🏆 杠杆点 2：建立乐理核心测试套件 + 修复算法 Bug (LV-1 + P0-2 + P0-3)

**理由**：`ChordClassifier` 和 `ModeAnalyzer` 是产品的大脑，但发现了两个严重的算法缺陷（4/4 拍硬编码、scaleName 被无视）。应当先建测试、再修 Bug，形成"测试驱动修复"的闭环。

**工作内容**：
- 在 CMakeLists.txt 中添加 Google Test 目标
